# E-Commerce Demand Forecasting & Inventory Decision System

An end-to-end data science project that forecasts daily product-level demand, validates forecasts using chronological time-series methods, and converts forecast uncertainty into an explicit inventory decision policy.

The project demonstrates:

* Data cleaning and validation
* SQL business analysis
* Time-series feature engineering
* Leakage prevention
* Model selection and chronological cross-validation
* Frozen final-test evaluation
* Forecast-error analysis
* Inventory simulation
* Stress testing
* Automated testing and reproducibility

> **Dataset note:** The project uses synthetic retail data. Synthetic data is used deliberately so the complete forecasting and inventory workflow can be reproduced without hiding assumptions about data provenance.

---

## Project Overview

The business problem is:

> **Given historical sales data, how can we forecast future product demand and use those forecasts as an input to an explicit inventory policy?**

The project follows this workflow:

```text

```

The forecasting target is:

```text
(date, product_id) → quantity
```

## Leakage Prevention

Leakage prevention is treated as a core modeling requirement.

For a prediction on date `t`, historical demand features may only use information available **before `t`**.

For example:

```text
lag_1 on January 20 = demand on January 19
```

Rolling statistics are calculated from shifted demand:

```python
shifted = quantity.shift(1)
```

so the target day's demand cannot enter its own rolling predictors.

The implementation also prevents future business attributes from being backfilled into earlier observations. Historical price values are forward-filled only; future prices are never used to populate earlier dates.

A regression test explicitly protects this behavior:

```text
tests/test_features.py
```

Same-day price, promotion, discount, and holiday variables are treated as known or planned inputs available at forecast time. This is a modeling assumption and is documented explicitly.

The final test period is also excluded from inventory uncertainty calibration.

# Validation Strategy

A random `train_test_split` is deliberately not used.

The forecasting problem is chronological:

```text
past → future
```

rather than a set of independently distributed observations.

Random splitting could allow training observations from later periods to influence evaluation of earlier periods.

## Development / Final Test Split

The final 60 days are kept as an untouched chronological test period.

```text
Development end:
2025-05-01

Final test:
2025-05-02 → 2025-06-30
```

The final test set is not used for:

* Model selection
* Feature selection
* Forecast-error uncertainty calibration
* Safety-stock calibration

## Expanding-Window Cross-Validation

Four chronological validation folds are run over the development period:

```text
Fold 1: 2024-09-04 → 2024-11-02
Fold 2: 2024-11-03 → 2025-01-01
Fold 3: 2025-01-02 → 2025-03-02
Fold 4: 2025-03-03 → 2025-05-01
```

Each fold trains on earlier observations and validates on a subsequent time window.

Implementation:

```text
src/forecasting.py::time_series_folds
src/run_time_series_cv.py
```

# Evaluation Metrics

### MAE

Mean absolute error, measured in demand units.

It answers:

> On average, how many units was the forecast away from actual demand?

### RMSE

Root mean squared error.

Because errors are squared before averaging, larger errors receive greater weight.

### sMAPE

A relative percentage-error metric used as an additional measure.

The implementation uses a small epsilon for numerical stability when demand is near zero.

# Inventory Decision System

The project converts the frozen demand forecast into a simplified periodic-review inventory policy.

Implementation:

```text
src/inventory_simulation.py
src/run_inventory_simulation.py
src/run_inventory_scenarios.py

notebooks/06_inventory_simulation.ipynb
```

The policy uses:

* 3-day lead time
* 7-day review period
* 10-day protection period
* Service-level z-value of 1.65
* Product-specific forecast-error uncertainty

## Forecast Uncertainty

Safety-stock uncertainty is estimated from development-period **out-of-fold Gradient Boosting predictions**:

```text
reports/gradient_boosting_oof_predictions.csv
```

The final 60-day test residuals are **not** used for safety-stock calibration.

This preserves the separation between development and final evaluation.

## Protection Period

The policy reviews inventory every seven days and assumes a three-day replenishment lead time:

```text
Protection period
= lead time + review period
= 3 + 7
= 10 days
```

Safety stock therefore accounts for uncertainty over the full protection period.

The implementation assumes approximately independent daily forecast errors when scaling daily error standard deviation across the protection period.

This is a simplifying modeling assumption rather than a claim about real retail demand.

# Inventory Simulation

The simulation is a **frozen-policy evaluation** over the final 60-day test period.

The forecast plan is fixed rather than dynamically reforecasting after every new observation.

The simulation reports:

* Average inventory
* Stockout days
* Cycle service level
* Lost units
* Units ordered
* Reorder point
* Target inventory level
* Safety stock

### Service Metric

The primary service metric is **cycle service level**:

> Percentage of simulated days without a stockout.

Cycle service level is different from fill rate, which measures the proportion of demand fulfilled.

# Business Interpretation

The project demonstrates how a demand forecast can become an operational input rather than an isolated model metric.

The analysis shows:

* Forecast error varies across products.
* Tree-based models reduce error relative to the Seasonal Naive baseline on this synthetic dataset.
* Inventory service changes when actual demand moves above the frozen forecast.
* Short-duration demand spikes can create substantial lost demand.
* Inventory-capacity constraints can materially reduce service levels.
* Forecast uncertainty can be incorporated into safety-stock calculations using development-period out-of-fold residuals.

The results should be interpreted as a methodological demonstration on synthetic data, not as evidence of expected performance for a real retailer.

# Limitations

## Synthetic dataset

The data generator creates controlled demand patterns and injected data-quality problems, but it does not reproduce every relationship found in real retail data.

Examples not modeled include:

* Product cannibalization
* Cross-product substitution
* Supplier constraints
* Stock-dependent observed demand
* Supplier lead-time variability
* Real promotion-planning processes

## Gradient boosting implementation

The project uses:

```text
sklearn.ensemble.HistGradientBoostingRegressor
```

It is a gradient-boosted-tree implementation and should not be described as XGBoost.

## Simplified inventory policy

The simulation does not explicitly optimize:

* Holding costs
* Stockout penalties
* Purchase-order costs
* Supplier minimum order quantities
* Multiple supplier constraints
* Shared warehouse capacity
* Stochastic lead times

## Frozen-policy simulation

The inventory scenarios evaluate a fixed forecast plan over the 60-day test period.

A production system would normally refresh forecasts as new observations arrive.

## Promotion information

Scheduled promotion information is assumed to be known when forecasting.

Real promotion calendars may be incomplete, delayed, or changed after the forecast is produced.

## Forecast uncertainty

The safety-stock calculation uses forecast-error standard deviation and assumes approximately independent daily errors when scaling uncertainty across the protection period.

A production system could replace this with:

* Prediction intervals
* Quantile forecasts
* Conformal prediction
* Probabilistic forecasting

# Interview Talking Points

### Why is this a time-series problem?

Observations are ordered in time, demand has temporal dependence and seasonality, and the production task is to predict future observations using information available before those observations occur.

### Why use a Seasonal Naive baseline?

A forecasting model should be compared with a simple operationally plausible baseline. Otherwise, absolute model error does not indicate whether additional model complexity provides useful improvement.

### Why use `lag_7`?

Retail demand often contains weekly patterns. The previous week's same weekday is therefore a natural baseline and predictor.

### How did you prevent target leakage?

Historical demand features use only information available before the prediction date. Rolling features operate on shifted demand, and future price values are never backfilled into earlier observations.

### Why not randomly split the data?

Random splitting breaks chronological structure and can allow training observations from later periods to influence evaluation of earlier periods.

### Why use tree-based models?

Tree-based models can capture nonlinear relationships and interactions between lagged demand, calendar variables, promotions, discounts, and other predictors without manually specifying every interaction.

### Why use MAE?

MAE is measured directly in demand units and is easy to communicate to business stakeholders.

### How was the final model evaluated?

Four expanding-window CV folds were used for development-period model assessment. The selected configuration was then frozen, retrained on the complete development period, and evaluated once on the untouched final 60-day test period.

### How was inventory uncertainty calibrated?

Development-period out-of-fold Gradient Boosting predictions were used to estimate forecast-error variability. Final-test residuals were not used for safety-stock calibration.

### Why is the protection period 10 days?

The policy uses a seven-day review period and a three-day replenishment lead time:

```text
3-day lead time + 7-day review period = 10 days
```

### What does cycle service level mean?

Cycle service level is the percentage of simulated days without a stockout. It differs from fill rate, which measures the proportion of demand fulfilled.

### What assumptions should you defend?

The main assumptions are:

* Synthetic data generation
* Known-at-forecast-time promotion information
* Fixed lead and review periods
* Frozen-policy inventory simulation
* Simplified forecast-error scaling
* No explicit holding-cost/stockout-cost optimization

These assumptions are documented rather than hidden.
